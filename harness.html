Agent Harness 工程师

造 AI Agent 的 可控底座：模型只负责产出「提案」，能不能执行由确定性校验、权限白名单、自愈回喂与熔断共同决定。做的是让 Agent 从「偶尔能跑」变成「可验收、可定位、可回滚」的那一层。

岗位职责

这个岗位具体做什么

Harness 不是「再包一层提示词」。它是 Agent 与真实系统之间的执行裁判层——下面六件事，每一件都有对应的作品与实测数据。

  • 任务编排与生命周期：把一次任务拆成可追踪的节点序列，管住启动、执行、中断、续跑与收尾。24 号用 LangGraph StateGraph 承载，每个节点状态可查，中断后能从断点续跑而不是从头再来。
  • 上下文与状态管理：上下文不是越长越好。按「必须保留 / 可压缩 / 可丢弃」分层，配合 MCP 白名单做上下文隔离——工具只能看到它该看到的那部分，避免上下文互相污染。
  • 工具调用治理：模型选工具、模型填参数，但参数要过 Pydantic Schema 校验；越权调用在白名单外直接拒绝。工具失败时只把结构化 error_stack 回喂，且附带 do_not_change 边界，防止模型顺手重构无关代码。
  • 确定性校验（关键取舍）：用 LLM 去校验 LLM 等于没校验。所以所有规则写成纯函数——Schema、业务规则、Linter 三道硬约束。代价是规则要人工维护、覆盖不到开放式语义问题，这是主动接受的成本。
  • 异常恢复与熔断：重试的边际收益下降很快，第 4 次之后基本是噪声，所以上限设在 3；超限转人工介入网关（Webhook 审批），而不是无限重试烧 Token。
  • 运行监控与门禁：OpenTelemetry + Jaeger 全链路 Span，Token / 耗时 / 调用链可下钻；597 个测试 + 82 个变异体覆盖 Python 3.11 / 3.12，评测集纳入 CI 门禁。

为什么强调「变异体全被杀」

测试通过不等于测试有效。变异测试会故意往代码里注入 bug，看测试能不能抓到——82 个变异体全部被杀死，说明这套测试真的在验证行为，而不是只跑了一遍覆盖率。对 Harness 这类「出错就是生产事故」的组件，这比行覆盖率更有说服力。

五层可控层怎么分工

模型只产出「提案」，能不能执行由下面五层决定。
层管什么对应 JD 要求
L1 工具编排与上下文隔离MCP 白名单 + 权限边界工具调用 / 权限控制 / 上下文管理
L2 确定性硬约束守卫Schema / 业务规则 / Linter，全部纯函数输出可信
L3 自愈反馈循环error_stack 结构化回喂 + do_not_change 边界异常恢复
L4 熔断与人工介入网关max_retries = 3，超限 Webhook 审批生命周期 / 异常恢复
L5 全链路可观测与 CI 门禁Token / 耗时 / Span / 回归断言运行监控

三处主动接受的取舍

  • 校验器必须是确定性的。用 LLM 去校验 LLM 等于没校验，所以规则全部写成纯函数。代价是规则要人工维护、覆盖不到开放式语义问题——这是主动换来的确定性。
  • 回喂要有边界。只丢原始报错，模型会顺手重构，改动面从 6 行变 60 行、回归风险翻倍；加上 do_not_change 后才收敛。
  • 熔断点设在第 3 次。重试的边际收益下降很快，第 4 次之后基本是噪声。代价是少数本可在第 4 次成功的任务被转人工——宁可转人工，也不无限烧 Token。

边界声明：24 号 Harness-Agent-Core 是本人自建参考实现与开源项目，非生产环境交付；外部系统（ERP / CRM / OA / 钉钉 / 企微）为桩实现，可现场演示。上面所有数字均为作品集实验口径。
